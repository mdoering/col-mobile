# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

iOS app (Swift 6 / SwiftUI / SwiftData) that browses the Catalogue of Life through the public ChecklistBank API and overlays GBIF occurrence data on taxon details. Single target, iOS 18+, iPhone-only. The wider CoL ecosystem (backend, ChecklistBank UI, portal, etc.) is described in the user-global `~/.claude/CLAUDE.md`.

## Building, running, and testing

The Xcode project is generated by **xcodegen** from `project.yml` — never hand-edit `CatalogueOfLife.xcodeproj/project.pbxproj`.

- After adding/removing/renaming source files: `xcodegen generate --spec project.yml`
- Build: `xcodebuild -project CatalogueOfLife.xcodeproj -scheme CatalogueOfLife -destination 'platform=iOS Simulator,name=iPhone 17' build`
- All tests: same command, replace `build` with `test`
- One suite or test: append `-only-testing:CatalogueOfLifeTests/SuiteName` or `-only-testing:CatalogueOfLifeTests/SuiteName/testName`
- Tests use Swift Testing (`import Testing`, `@Suite`, `@Test`, `#expect`) — not XCTest. Tests must build cleanly; if a protocol change makes the stubs (`CatalogueOfLifeTests/Helpers/Stub*Client.swift`) fail to conform, fix the stubs in the same change.

When the user wants to actually run the app, ask them to launch it in Xcode — `xcodebuild` only builds; the simulator boot + install dance from the command line is more friction than it's worth.

## Architecture

Layered, with strict directional dependencies (top → bottom):

1. **Views** under `CatalogueOfLife/Features/<Tab>/` and shared `Components/`. SwiftUI only. Each feature owns one `@Observable @MainActor` view model in the same folder.
2. **AppState** (`App/AppState.swift`) — singleton `@Observable` injected via `.environment`. Holds the selected dataset, user preferences (vernacular language, map styles, search content mode, base-map opacity), and `pendingSearch*` shuttle values used to cross-tab navigate. Every persisted preference uses the `didSet { defaults.set(...) }` pattern with a key in the private `Keys` enum.
3. **Networking** (`Networking/`) — two protocols, `APIClient` (ChecklistBank, `api.checklistbank.org`) and `GBIFClient` (`api.gbif.org`). View models depend on the protocols, never on `*Live` directly. URL building lives in `Endpoints` / `GBIFEndpoints`; everything goes through `HTTPSession.shared`.
4. **Models** split into `Models/DTOs/` (wire shape, `Decodable`) and `Models/Domain/` (app-internal value types). DTOs convert to domain via `extension Domain { init(dto:) }`. `PagedDTO` handles the API quirk that the `result` key is omitted entirely on zero-hit responses — same pattern is used for `NameSearchResponseDTO`.
5. **Persistence** (`Persistence/`) — SwiftData via `PersistenceStore.shared`, schema is **versioned** (`PersistenceSchemaV1` + `PersistenceMigrationPlan`). Adding/changing a `@Model` requires a new schema version + migration stage; do not edit the v1 entities in place once shipped.

### Patterns to follow

- **Cold-launch race**: `AppState.loadReleases()` is async and sets `selectedDatasetKey` only after the dataset list resolves. Views that need the key use `.task(id: appState.selectedDataset?.key)` rather than `.task` so they re-fire when the key arrives.
- **Release aliases**: `"3LXR"` and `"3LR"` are server-side aliases that resolve dynamically to the latest extended/base release on each `/dataset/{alias}` call. The numeric `selectedDatasetKey` is what's persisted; the alias-to-key mapping is re-resolved every launch (so a user pinned to "Latest Extended" auto-advances when a new release ships).
- **Tab cross-navigation**: views set `appState.pendingSearchScope` / `pendingSearchGroup` / `selectedTabIndex`, and the destination view reads + clears them in a `.task(id:)`.
- **Map regions**: every region applied via `MKMapView.setRegion` must pass `MKCoordinateRegion.isValidForMap` (defined in `GBIFMapView.swift`). The GBIF capabilities bbox can extend past ±180° for transpacific species — `init?(capabilities:)` already falls back to `worldExcludingPoles` in that case.

### Testing

- `CatalogueOfLifeTests/Helpers/StubAPIClient.swift` and `StubGBIFClient.swift` conform to the live protocols. Any protocol signature change must update both — the stubs are the integration point that catches breakage at compile time.
- JSON fixtures in `CatalogueOfLifeTests/Fixtures/` are loaded via `FixtureLoader.data(_:)`. New decoder tests should prefer fixtures over inline JSON when they cover real-world response shape; small structural cases can use inline JSON.
- View-model tests are `@MainActor` and drive the VM directly with a stub client.

## Bundled JSON snapshots

Two bundled snapshots live under `CatalogueOfLife/Resources/Bundle/`:

- `taxgroup_vocab.json` — the TaxGroup vocab + per-group SVG icons (rendered into the asset catalog under `Assets.xcassets/Groups/`). Refresh with `Tools/bundle_taxgroup_assets.py` when upstream adds groups.
- `release_timeline.json` — historical release metadata for the Metrics tab's timeline chart. Refresh with `Tools/bundle_release_timeline.py` when a new release ships.

Both scripts are stand-alone Python 3 with stdlib only.

## Conventions

- The repo uses Swift 6 with `SWIFT_STRICT_CONCURRENCY: complete`. View models are `@MainActor`; clients are `Sendable` actors or `@unchecked Sendable` stubs.
- Commit subjects follow the pattern `Area: short imperative`, optionally with a body explaining the *why*. See `git log` for examples.
- Design docs and historical implementation plans live under `docs/superpowers/specs/` and `docs/superpowers/plans/`. Treat them as historical context, not a spec to follow blindly — the code has evolved past them.
